# Direct3D 9 behind the game — spike and plan

The game talks Direct3D 8, and our plugins are held to what Direct3D 8's fixed-function
pipeline can do: eight lights per draw, lighting per vertex, no shaders of our own. The
limits `lighting/README.md` keeps running into all come from there. The aim here is to keep the
game's code as it is and let plugins **use Direct3D 9 with shaders** for the draws they
own, while everything else renders exactly as it does today.

The route is a d3d8-to-d3d9 translator in the d3d8 slot, with DXVK's d3d9 behind it:

    Armada2.exe
      -> <game dir>/d3d8.dll      crosire's d3d8to9 (BSD-2-Clause)
      -> <game dir>/d3d9.dll      DXVK d3d9
      -> Vulkan

Today DXVK's own `d3d8.dll` sits in that slot (`README.md`, "The d3d8 chain"). Both the
translator and DXVK's d3d8 end in DXVK's d3d9, so `dxvk.conf`, vkBasalt bloom and the
Vulkan path are unchanged. What changes is that a plugin can reach the d3d9 device.

## The spike (2026-10-05)

On the bench (`testbench/d3d9probe/`), at 1920x1080, every layer installed from `main`
(lighting 1.4.0), three d3d8 DLLs were compared. The game, the plugins and DXVK's
`d3d9.dll` were the same for all three.

| | DXVK d3d8 (today) | GOG's d3d8to9 | crosire's d3d8to9 v1.16.0 |
|---|---|---|---|
| what it is | DXVK's own D3D8 front end | crosire's code, 2022 build, with Microsoft's D3DX linked in statically (1.1 MB) | the upstream release, 125 KB, D3DX loaded at run time from `d3dx9_43.dll` |
| game, every plugin | runs | runs | runs |
| `QueryInterface(IDirect3DDevice9)` on the game's device | `E_NOINTERFACE` | `E_NOINTERFACE` | **the d3d9 device** |
| may we ship it? | already ships with Heroic/Proton | it is the player's own file, but cannot be vendored: its D3DX is Microsoft's | **yes**: BSD-2-Clause, vendored under hard rule 8 |

DXVK's d3d8 answers only to its own interfaces: its wrapped objects throw on any other
interface ID (`D3D8WrappedObject::GetInterface` in DXVK's source). Reaching its d3d9
would mean reading a private field of one DXVK build. Upstream d3d8to9 has forwarded
unknown IDs to the d3d9 object since 2019. GOG's build refused anyway, and why wasn't
pursued: it can't be shipped either way.

**On crosire's v1.16.0, measured:**

- **Caps.** The device answers with DXVK's d3d9 device. It reports vertex shader 3.0
  with 256 constants, pixel shader 3.0, 8 fixed-function lights and 8 textures.
- **Shaders.** Hand-assembled `vs_3_0`, `ps_3_0` and `ps_2_0` shaders, a vertex
  declaration and a `D3DSBT_ALL` state block were all created without error.
- **Overlay.** A per-pixel shaded quad drew into the game's frame on every `Present`, on
  the 8x MSAA back buffer `MSAA.asi` sets up. Nothing around it changed.
- **Per-draw shader swap.** In the middle of the scene, a `ps_2_0` shader was swapped
  into each textured indexed draw, about 7 per frame in the planet scene. The game's
  textures and fixed-function vertex lighting fed into it. The Galaxy class (drawn by
  `Lighting.asi`'s vertex buffers) and the planet came out tinted, with their texture and
  shading intact.
- **Everything else matched DXVK's d3d8, compared shot for shot.** Covered:
  - `Menus.asi` (`hooks=7/7`, `embed=1`) and the Bink menu backdrops;
  - Instant Action setup and the match;
  - the HUD, the grid bar, the minimap, box selection and the cursor;
  - `MSAA.asi` (8x, edge fill), `Lighting.asi` (11 call sites);
  - phasers and shields in the `firing` scene.
- **Logs.** DXVK's log shows the same two warnings on both chains (render states 26 and
  136, unhandled). Wine logged no errors, and nothing failed to load.
- **Frame time.** 16.7 ms on both chains. The bench is vsync-bound, so this only shows
  that neither drops frames; it says nothing about throughput.

**Differences to keep in mind:**

- **D3D8 compatibility mode.** Under DXVK's d3d8, DXVK's d3d9 runs in "D3D8
  compatibility mode"; under the translator it doesn't. Nothing visible changed in the
  scenes above. A full scenario run is how this gets checked, not an argument.
- **`d3d8.*` keys in `dxvk.conf`** would stop applying (none are set today).
- **The minimap read-back** (`msaa/README.md`) goes through crosire's `CopyRects`. That
  uses `StretchRect` for default-pool surfaces, and D3DX (Wine's builtin
  `d3dx9_43.dll`) for a managed or system-memory destination. The minimap drew
  correctly; which branch it takes isn't logged yet.
- **Dependencies.** The release needs `msvcp140`/`vcruntime140` and `d3dx9_43`. Proton
  has all three as builtins. A Windows player needs the VC++ 2015–2022 runtime and the
  DirectX end-user runtime, but no DXVK: the translator runs on Windows' own d3d9.

**Not covered by the spike:**
- the launch reels and campaign cutscenes (the bench launches with `-nointro`);
- `Reset` (not exercised under DXVK either, `msaa/README.md`);
- a mission's end;
- multiplayer;
- an hour of play;
- frame rate with vsync off.

**Shaders can be built here.** `vkd3d-compiler` (Arch `vkd3d` 1.19) compiles HLSL to
legacy bytecode (`-x hlsl -b d3dbc -p vs_3_0|ps_3_0`). Its output isn't optimised
(redundant moves), which shader model 3.0's instruction budget absorbs. Compiled at build
time and embedded as byte arrays, the shaders need no compiler at run time.

## The plan

Each phase ships and is confirmed in game on its own, and each leaves the game working
if the next is never done. **Any plugin that uses d3d9 must fall back to what it does
today when the `QueryInterface` fails**, so DXVK's d3d8 and GOG's chain keep working
and `d3d8-chain.py --use dxvk` stays a one-command way back.

### Phase 0 — the chain (platform)

**Status (platform 3.2.0):** done. `./install` makes the d3d8to9 chain the default for a
game on the DXVK chain (`d3d8-chain.py --upgrade`, platform `README.md`); it was confirmed
in game 2026-10-05 together with lighting 1.5.0 to 1.8.0. Re-running `./install` moves an
install across, so this is a MINOR bump, not the MAJOR planned below. The release zip's
installer is unchanged: it would need the Windows runtimes and the lighting layer first.

Earlier status (platform 3.1.0): steps 1 and 2 were done except the default, and step 4
measured. By decision, step 3 is not a full scenario run: the bench checks below, then
play. The default stays DXVK's d3d8 until it is confirmed in game; `--use d3d8to9`
is one command, and the release zip's installer is changed only with the default
(it installs `MSAA.asi` only beside DXVK's d3d8, and would skip it here).

1. **Vendor the translator.** Put crosire's d3d8to9 release under
   `platform/vendor/d3d8to9-1.16.0/` with `LICENSE.md` and a `SOURCE.txt` (release URL,
   sha256), as hard rule 8 requires. Don't vendor GOG's file (its D3DX is Microsoft's).
2. **Teach `d3d8-chain.py` the new link.** Add `--use d3d8to9`, identified by hash like
   every other link, and make it the default the install sets. `--use dxvk` stays
   available.
3. **Run the scenario suite on it:**
   - every scenario in `testbench/scenarios/`, the multiplayer ones included;
   - `./a2test run no-assets`;
   - a campaign mission through to its end and its cutscene;
   - the launch reels.

   Add a line to the probe log saying which `CopyRects` branch the minimap takes.

   Logged 2026-10-05 (the first call of each pair of surfaces, every failure): in a
   whole Instant Action match on d3d8to9 the only `CopyRects` were `MSAA.asi`'s
   edge fill, four 1-pixel strips a frame between 8x MSAA default-pool surfaces, all
   through `StretchRect` and all succeeding. The minimap's read-back did not run in
   that match, and the minimap drew. If it ever runs and fails it will be in the log;
   until then it is a thing to watch for in play, not a known break.
4. **Measure frame time with vsync off** on both chains, in a busy match. That is the
   one cost the spike couldn't see.

   Measured 2026-10-05 in the `firing` scene at 1920x1080 with every layer, vsync off
   (`D3D9PROBE_TIMING=1`), about 69,000 frames each: **1.00–1.09 ms a frame on both
   chains**, means per 600 frames, with no trend. Both sit on the same floor, which
   looks like the game's own frame limit rather than either renderer, so this says the
   translator costs nothing visible in that scene, not what a heavier one would show.

**Versioning:**
- **platform** gets a MAJOR bump: the chain the install sets changes, and a player has to
  re-run it.
- **Plugins** don't change in this phase.

**Done when:** you have played on it and confirmed it.

### Phase 1 — the d3d9 device for plugins

A small shared piece (a header each plugin includes) does three things:
- **Gets the device.** From the `IDirect3DDevice8` the engine already holds, it asks
  once per device for `IDirect3DDevice9`, and caches the answer until the next
  `CreateDevice`/`Reset`.
- **Saves and restores state around a draw we own.** It restores the vertex shader, the
  pixel shader, the declaration and the constants we touched, with `Get`/`Set` as the
  probe does for the pixel shader. The translator keeps its own record of what's bound,
  so whatever we change must be back before the game's next call.
- **Holds embedded shader bytecode.** It creates the objects lazily per device and
  releases them on `Reset` and device loss.

`build.sh` compiles `*.hlsl` with `vkd3d-compiler` into a generated header, and fails
when the compiler is missing.

**Status (platform 3.1.0): built.** `platform/d3d9/d3d9dev.h` is the header and
`platform/d3d9/hlsl.sh` the compiler step. `D3D9Probe.asi` uses both: its shaders are
HLSL now, and on the bench (2026-10-05, `firing` scene, d3d8to9) the overlay drew and
the tint ran on 2880 draws through `d9_save`/`d9_bind`/`d9_restore`, the hulls red and
nothing else changed. One finding shaped the header: the engine sets its vertex
format through d3d8 `SetVertexShader(FVF)`, which d3d8to9 turns into d3d9 `SetFVF` +
`SetVertexShader(NULL)`, so a plugin binds its shaders in a hook on the draw call, not
around the engine's render function. A `vs_3_0` reads the game's vertex buffer through
the FVF as it is; no declaration of ours is needed.

### Phase 2 — `Lighting.asi` in shaders

**Status (lighting 1.5.0): the first step is built.** `Shaders=1` runs the hull draws
in shaders that reproduce the fixed-function result per pixel, with the lights read back
from the device, so nothing about the lights changes yet; bench A/B and the trace are in
`lighting/README.md`, "Shaders". The items below that change the look (the normal
negation, more point lights, the self-illumination alpha) come next, each judged in game.
The first step was confirmed in game 2026-10-05. **Lighting 1.6.0** does the normal
negation and the point lights (up to 16, falloff per pixel), confirmed in game
2026-10-05; **1.7.0** the self-illumination alpha, which completes phase 2's list.

The draws `Lighting.asi` already owns, the `ST3D_Standard_MeshVB` ones, get a
`vs_3_0`/`ps_3_0` pair in place of fixed-function lighting:

- **Inputs.** The vertex buffer as it is (position, normal, UV). The transforms come
  from `GetTransform` at draw time, because the engine still sets them as fixed-function
  state.
- **Lighting per pixel.** Key, Fill and Sky, plus the point lights `pick_points` already
  chooses: up to about 24 per draw instead of 5, held in pixel shader constants. Each
  light keeps the falloff and strength the ini keys set.
- **Inward normals.** The shader negates the normal once. That replaces the mirroring
  trick for soft lights, and finally lights the right side for **hard lights**
  (torpedoes, pulses), the open item in `lighting/README.md`. `FixMirrored` becomes a
  sign in a constant.
- **What the fixed-function stages did, reproduced.** Phase 2 starts with a
  `testbench/d3dtrace` frame of these draws. It lists their texture-stage ops (the hull
  alpha is a self-illumination map), their blend states and whether fog is on. A
  `ps_3_0` replaces all of the fixed-function pixel stage, fog included, so each case the
  trace shows needs a shader variant.
- **Switchable.** A new key, `Shaders=1` (lighting MINOR). With `0`, or with no d3d9
  device, the fixed-function path runs as in 1.4.0.

**Checked by:** bench shots of the `planet`, `nebula` and `firing` scenes against the
fixed-function path, then a test in game. Expect to judge the look again: per-pixel
lighting shows the low-poly hulls' faceting less and close point lights more.

### Phase 3 and later — what this opens up (each a decision of its own)

- **Planets** (CPU-lit, `LightVertices_Lambert`) on the same shader path: a soft
  terminator and the night side per pixel.
- **Normal and specular maps** for hulls, built by the texture pipeline as their own
  targets into `$A2_DATA`. A height map derived from hull art was rejected once on the
  dot3 path (`models/README.md`). Per-pixel lighting with our own falloff is a different
  test, but the bar is the same: in game, at the real on-screen size.
- **Shadows** from the key light for ships and stations: a depth pass of the draws we
  own.
- **Effects that need depth** (ambient occlusion, depth-aware bloom), which vkBasalt
  can't see.

## Risks

- **The translator is a second implementation of Direct3D 8**, and DXVK's d3d8 has been
  tuned on far more D3D8 games. The scenario suite and a playthrough are the check. The
  chain switch is one command either way.
- **State leaking between our d3d9 calls and the game's d3d8 calls** is the
  likeliest kind of bug, and it would look like a wrong blend or a missing HUD element
  rather than a crash. Phase 1 keeps every touch in one place for that reason.
- **Native Windows players** need the two Microsoft runtimes. If the install sets up the
  chain on Windows, it should check for them.
